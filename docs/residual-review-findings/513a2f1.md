## Residual Review Findings

- P2 — `backend/app/services/translation_service.py:145` — **Aggregate batch can approach the 600s Ollama timeout.** One batched generation now carries the whole field map, so a large CV that previously failed per field can fail all-or-nothing after the full `OLLAMA_TIMEOUT_SECONDS` (600s at ~2.2 tok/s). Chunking is explicitly deferred by the Product Contract's Scope Boundaries; the plan's precompute-on-save fallback remains the next step if measurement shows a normal CV exceeds 20s.
- P3 — `backend/app/services/translation_service.py:50` — **`num_predict: 2048` exceeds the timeout budget.** At ~2.2 tok/s, 2048 output tokens is ~930s, longer than the 600s timeout, so the timeout binds before the cap and the cap does not protect against truncation as its comment implies. Consider aligning the cap with the timeout or detecting truncation via the response finish reason.
- P3 — `backend/app/services/llm_client.py:127` — **Process-wide Ollama lock held for the whole batch.** The lock is now held for the full multi-minute generation instead of being released between fields, so a concurrent CV parse or cover-letter generation waits for the whole batch. Accepted for the documented single-user deployment; revisit if concurrency matters.
- P3 — `backend/app/services/llm_client.py:139` — **Truncation (`done_reason == "length"`) is not detected.** A response cut off at the output cap is retried blindly and then surfaced as an opaque per-field error; logging or handling the finish reason would make the failure observable.
